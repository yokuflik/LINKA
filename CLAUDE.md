# CORE BEHAVIOR RULES

1. **Memory & Context:** Always summarize important architectural decisions, database schema updates, and key context in the `CLAUDE.md` file before concluding a major task. Treat it as your persistent external brain.
2. **No Yapping:** Be extremely concise. Output only the necessary code or commands, accompanied by a 1-sentence explanation maximum. Skip all pleasantries, apologies, and overly verbose explanations.
3. **The 3-Strike Rule (Anti-Loop):** If you execute commands and encounter an error on the exact same issue 3 times in a row, DO NOT attempt another fix. Stop immediately, explicitly state that you are stuck in a loop, and ask the user for guidance.
4. **Code Standards:** Write all source code comments exclusively in English.
5. **Targeted Edits:** For small tasks, minor features, or bug fixes, NEVER rewrite or output the entire file. Use targeted diffs or provide ONLY the specific code blocks/functions that need to be updated.
6. **Frontend Display Rule:** NEVER display the raw `user_id` in the UI (e.g., in chat lists, message bubbles, or headers). For UI display purposes, ALWAYS use the `phone_number` or, preferably, the resolved human-readable name from the local contacts dictionary. The `user_id` is strictly for backend logic and API calls.
7. **No Autonomous Visual Testing:** NEVER use browser tools, Puppeteer, or take screenshots to test frontend changes. Do NOT attempt to spin up local servers to visually verify the UI. The user will manually test the application in their own browser and report back any visual, UI, or functional issues.

# Linka

A real-time messaging platform (WhatsApp/Telegram-style), designed for tens-of-billions-of-messages scale. Built incrementally, backend-first — **there is no real client app**, only a single-file HTML/Vue PoC for manual testing.

## Stack
FastAPI (REST + WebSocket) · PostgreSQL 15 via SQLAlchemy 2.0 async/asyncpg · Redis 7 (presence, pub/sub fan-out, rate limiting, idempotency, OTP) · PyJWT · Pydantic v2 · pytest/pytest-asyncio/httpx for tests.

## Layout
- `database/models/`, `database/crud/` — User, Chat, Participant, Message (RANGE-partitioned by `created_at`), PrivateChatPair (race-free 1:1 chat dedup)
- `services/` — business logic: `auth_service`, `user_service`, `chat_service`, `message_service`, `presence_service`, `realtime_service` (Redis pub/sub), `rate_limit_service`, `notification_service` (push stub), `connection_manager` (per-process WebSocket state)
- `routers/` — REST (`auth`, `users`, `chats`, `messages`) + `websocket` (`/ws`), thin pass-throughs to services; error→HTTP mapping centralized in `main.py`
- `poc/index.html` — Vue 3 + Tailwind (both via CDN) test client entry point, no build step. All `setup()` state/logic (auth, WS, presence, chats, messages, members, receipts) lives here; template markup is split into `poc/components/*.js` (see below).
- `poc/components/*.js` — plain `Vue.defineComponent({...})` objects (not `.vue` SFCs — no build step to compile them), one per UI section: `AuthScreen`, `AppHeader`, `ChatSidebar`, `ChatHeader`, `MessageList`, `MessageInput`, `MembersModal`, `ToastList`. Loaded via `<script src>` tags in `index.html` before the root `createApp` script, registered in `components: {}`, and wired with props down / emits up — root `index.html` is still the only place owning state. `MessageList` exposes its scrollable element as `messagesEl` (via `expose: [...]`) since the root's `scrollMessagesToBottom()` needs to reach into it (`messagesEl.value.messagesEl`) now that the div moved out of the root template.
- `utils/snowflake.py` — custom Snowflake ID generator
- `scripts/init_db.py` — creates/drops schema (no Alembic migrations exist); `scripts/seed_mock_data.py` — fills it with 5 users, private/group chats between them and a backdated message history (safe to re-run)
- `tests/` — 197+ tests, all against real Postgres/Redis containers (no mocks)

## Running locally
```bash
docker compose up -d                                    # test_db (5433), test_redis (6380)
DATABASE_URL="postgresql+asyncpg://test_user:test_password@localhost:5433/test_db" python3 -m scripts.init_db
DATABASE_URL="..." REDIS_URL="redis://localhost:6380/0" uvicorn main:app --reload
```
Open `poc/index.html` directly in a browser (CORS is wide open, dev-only). OTP codes print to the server console (`[STUB] Would SMS OTP ...`) — no real SMS/FCM provider is wired up.

**`uvicorn --reload` drops every open WebSocket on each file save** — if testing live and something edits a `.py` file, expect the PoC's connection to drop and auto-reconnect (~3s). Not a bug.

## Known gaps (deliberately not built)
- No REST routes for sending/editing/deleting messages — that's WebSocket-only by design.
- No `call_service.py` / `media_service.py` (WebRTC, S3 uploads) — explicitly deferred.
- No DB migrations — schema only via `scripts/init_db.py`; no automated partition management for `messages`. `create_all` never alters an existing table, so a new column on an existing dev DB needs a manual `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (or a `--drop` + re-init, which loses the data).
- `message_service._fan_out` is synchronous with `send_message` (not queued) — a deliberate call, not yet revisited (see fan-out decision in memory).
- **Contact Discovery was requested and abandoned mid-spec, nothing built**: a `DeviceContactsProvider` frontend service mocking a device-contacts API (phone numbers `"1"`-`"10"`), a `POST /contacts/sync` backend endpoint to match them against registered users, and a "My Contacts" UI section with a "Start Chat" button. The request was interrupted before any code was written. Don't assume any of it exists.

## Things worth knowing about the chat list
- `Chat.last_message_preview` (first ~120 chars of the last message's content) and `Chat.last_message_status` (see receipts below) are both denormalized onto `Chat` for the same reason as `last_message_id`/`last_message_at`: resolving them from `messages` per listed chat would hit a RANGE-partitioned table with no partition to prune to. `last_message_preview` is kept in sync on edit/delete too (`crud_message.edit_message_content`/`soft_delete_message` rewrite/clear it, but only when the edited/deleted message is actually the chat's current `last_message_id`).
- The PoC's contact "names" (`MOCK_CONTACT_NAMES` in `poc/index.html`, e.g. phone `"1"` → "Daniel Cohen") are a **client-only lookup with nothing behind it on the server** - it fires whenever a phone number/id happens to be the literal string `"1"`-`"10"`, regardless of that user's real `display_name`. `scripts/seed_mock_data.py`'s `CONTACT_NAMES` dict is a duplicate of the same ten names/numbers, kept manually in sync, so the seeded data actually exercises the mapping (five real registered users with phone numbers `"1"`-`"10"`, each with a private chat to every one of the five main `MOCK_USERS`). Don't be surprised to find users with plain single/double-digit phone numbers in the dev DB - they're intentional.

## Things worth knowing about delivery/read receipts
- `MessageStatus` (`database/models/message.py`: SENT/DELIVERED/READ — WhatsApp's one grey / two grey / two blue checks) is **derived, never stored on `Message`**. Storing it directly would mean writing to that row every time it crosses a threshold — in a group, that threshold is "every one of up to ~1000 participants," on a table sized for tens of billions of rows.
- Instead, `Participant` carries two per-user watermarks — `last_read_message_id` (pre-existing) and `last_delivered_message_id` (mirrors it) — and `Chat` carries their chat-wide rollup: `all_delivered_up_to_message_id` / `all_read_up_to_message_id`, each the `MIN(...)` of that watermark across the chat's current participants ("the highest message id literally everyone has delivered/read"). `crud_message.compute_message_status(message_id, chat)` then just compares a message's id against those two chat columns — O(1), independent of group size or history length.
- `crud_participant.recompute_chat_receipt_cursors` is what maintains those chat-wide columns, called after every `update_last_delivered_message`/`update_last_read_message`/`remove_participant`, and from `crud_message.create_message` (sending implies having seen the chat up to that point, which auto-bumps the sender's own watermarks and can itself unstick a cursor that was stuck on the sender's stale one).
- `add_participant_to_chat` seeds a new participant's watermarks at the chat's *current* `last_message_id`, not `NULL`/0 — otherwise adding one new member to an already fully-read 1000-person group would reset both cursors to "nothing," making years of history report as unread again. Don't remove that seeding.
- WebSocket actions: `mark_delivered` and `mark_read` (both `{chat_id, message_id}`), each firing a `delivery_receipt`/`read_receipt` fan-out event. The `new_message` fan-out event also carries `status` (always `1`/SENT at that instant - the cursors can't already cover an id that didn't exist a moment ago).
- Exposed over REST: `MessageOut.status` (`GET /chats/{id}/messages`, always attached by `message_service.get_message_history`) and `ChatOut.last_message_status` (only ever attached by `chat_service.get_chat_list` - the `POST`/`PATCH` chat endpoints that also return a `ChatOut` don't have participant-watermark context loaded, so it's `None` there, not a guess).
- The PoC (`poc/index.html`) renders the tick (✓ / grey ✓✓ / blue ✓✓) under each of *your own* sent messages, and auto-sends receipts: `mark_delivered` the instant a `new_message` event reaches the socket (regardless of which chat is open - that's the point of "delivered"), `mark_read` additionally when that chat is the one on screen, and both for the newest message whenever a chat is opened (`selectChat`, to catch up on anything missed). On a `delivery_receipt`/`read_receipt` event for the open chat, it re-fetches that page's statuses (`refreshMessageStatuses`) rather than guessing client-side which of the sender's own messages actually changed - a single event only tells you one participant's watermark, not whether that made this chat's aggregate cross a threshold.
- `markAllChatsDelivered` (poc/index.html) sends `mark_delivered` for *every* chat's `last_message_id` on login/reconnect, not just whichever chat is open - without it, messages sent to you while offline stayed stuck at "sent" until you manually opened each chat, since the live `new_message`/`selectChat` paths only ever covered one chat at a time. Called from both `ws.onopen` and after `loadChats()` resolves, to cover the race between "socket ready" and "chat list loaded" regardless of which finishes first.

## Things worth knowing about group membership / system messages
- Clicking a group's title in the PoC opens a members modal (`GET /chats/{id}/members`) showing each member with a role badge (1=Member/none shown, 2=Admin, 3=Owner). No new router/schema was needed — `POST /chats/{id}/members` (add), `PATCH /chats/{id}/members/{user_id}` (role change) already existed and already enforce the right roles server-side (`chat_service._require_role`: add/remove need `ROLE_ADMIN`, role change needs `ROLE_OWNER`). The PoC's gating (`canManageActiveChatMembers` ≥2, `canChangeActiveChatRoles` ===3) exists only to hide buttons that would 403 — it is not itself a security boundary.
- Clicking a member row (if you can manage members) opens a small options popup: "Make/Remove admin" is wired to the role-change PATCH; "Remove from group" calls `DELETE /chats/{id}/members/{target_user_id}` (see leave/remove section below) and is gated client-side by `canRemoveMember`/`hasMemberOptions` so it only ever shows where the call would actually succeed.
- `Message.sender_id = NULL` + `type = SYSTEM_MESSAGE_TYPE` (6, `services/message_service.py`) marks a system message ("X joined the group", etc.), sent via `message_service.send_system_message` and fanned out over the normal `new_message` WS event like any other message. The PoC renders these as a centered small gray pill (WhatsApp-style), not a chat bubble (`sender_id == null` branch in the message `v-for`).
- System-message `content` embedding a raw user id was a real bug — `chat_service._display_name_for(session, user_id)` (resolves `display_name` or falls back to phone number) is used everywhere a system message names someone, so `add_member`'s message reads `"{actor_name} added {new_member_name} to the group"`.
- **`role_changed` is a private system message, not a broadcast one**: `chat_service.change_member_role` sends a system message whose `content` is JSON (`{"kind": "role_changed", "actor_id", "target_id", "new_role"}`) instead of plain text, because it's only meant for the two people involved, not the whole chat — but the fan-out mechanism has no concept of a per-recipient message, so it still reaches everyone's socket. The PoC's `shouldShowSystemMessage(m)` is what actually enforces the privacy: it parses the JSON and renders nothing unless `currentUser.id` matches `actor_id`/`target_id`; `systemMessageText(m)` then builds the human-readable "You made X an admin"/"X removed you as admin" line client-side. If a future system-message kind needs the same treatment, follow this same JSON-content + client-filter pattern rather than adding a DB column (there's no structured metadata field on `Message`, and adding one hits the no-migrations gap above).
- System messages must never overwrite `Chat.last_message_preview` (a chat list showing "X was made admin" instead of the last real message is a bug, not a feature) — fixed at the source: `crud_message.create_message` only updates `last_message_preview` when `sender_id is not None`; `last_message_at`/`last_message_id` still update either way (system messages should still bump the chat to the top of the list). The PoC mirrors this on the live-update path: `handleWsMessage` only calls `bumpChatPreview` when `msg.sender_id != null`.

### Leaving a group / removing a member
- One endpoint handles both: `DELETE /chats/{chat_id}/members/{target_user_id}` (`routers/chats.py` → `chat_service.remove_member`). `actor_id == target_user_id` is a self-leave and skips the role check entirely; otherwise the actor needs `ROLE_ADMIN`, **and** server-side (not just client-side) `remove_member` now also requires `target.role < actor.role` — an admin can remove a plain member but not another admin or the owner, only the owner outranks an admin. This rank check has no DB constraint behind it (nothing stops a direct `crud_participant.remove_participant` call from bypassing it) — it's enforced only in this one service function.
- **The owner can never leave a non-empty group without naming a successor.** Self-leave as `ROLE_OWNER` with other participants still in the chat requires a `new_owner_id` query param (validated as an actual member) — omitting it raises `chat_service.OwnershipTransferRequiredError` → HTTP 409. The successor is promoted via `update_participant_role` and a plain-text broadcast system message ("X made Y the group owner") is sent, *before* the owner's own row is removed.
- **Whenever a removal (self-leave or admin-kick) leaves the chat with zero participants, the whole chat is deleted** (`crud_chat.delete_chat`, which cascades to `Participant` and `Message` via `ON DELETE CASCADE` FKs) instead of sending a system message into a chat nobody will ever read again. This is the same code path whether it's "last member left" or "owner left alone with nobody to inherit it" — both just fall out of the post-removal `remaining participants == 0` check, no separate branch needed.
- Both the leaving/removed user and — on ownership transfer — the whole chat get told live: `chat_service._notify_removed_from_chat(user_id, chat_id, actor_id, chat_title)` publishes a `removed_from_chat` personal-channel event (mirrors `_notify_added_to_chat`'s `added_to_chat`), which `connection_manager._handle_user_channel_event` uses to unsubscribe that user's live connections from the chat immediately (not just at next reconnect) and forwards to the client. The PoC's `handleWsMessage` drops the chat from the sidebar, clears it if it was the active chat, and toasts `You were removed from "{chat_title}"` — but only when `msg.actor_id !== currentUser.id`, since a self-initiated leave (`leaveActiveGroup`) already updated that same device instantly and doesn't need to be told about its own action.
- PoC leave flow: the red "Leave group" button (`startLeaveGroup`, under the member list in the members modal, shown to every member regardless of role) checks if the current user is the owner with other members present — if so it shows an inline "pick who takes over" `<select>` + "Transfer & leave"/"Cancel" instead of leaving immediately; otherwise (not owner, or owner alone) it confirms and leaves directly, passing `new_owner_id` as a query param only in the transfer case.

## Things worth knowing before touching auth
- Every 64-bit Snowflake id is sent as a **JSON string** on the wire (REST responses and WebSocket, both directions) — never as a JSON number. A number silently loses precision in JS past 2^53. See `routers/schemas.py`'s `IdStr` and the header comment in `poc/index.html`. Never `parseInt()`/`Number()` an id anywhere in the PoC.
- `auth_service.verify_otp_and_login`'s code-comparison check (`stored_code != code`) has been found commented-out twice during manual testing (not by Claude) — always sanity-check this line is live before treating OTP auth as secure.
- `connection_manager` uses a per-user Redis channel (`user_events:{user_id}`) so a chat created *after* a WebSocket already connected still reaches it live (dynamic re-subscription). This is what makes new chats/group invites show up without a reconnect.

## Presence — Subscribe-on-Demand (backend + PoC UI both built)
- **1:1 only, never global fan-out.** Connecting/disconnecting a WS does NOT broadcast online/offline to any chat or contact list — nothing is pushed proactively on connect/disconnect to anyone who hasn't explicitly asked. Presence state itself is still the pre-existing ephemeral Redis tracking in `presence_service` (`presence:{user_id}` set of connection_ids + TTL, multi-device aware — the user is only "offline" once every connection is gone).
- New in `presence_service`: `presence_last_seen:{user_id}` (a plain string timestamp, no TTL, written only on the 0-connections transition) and `get_status(user_id)` → `{"status": "online"|"offline", "last_seen_at": iso-str|None}`, used for the initial pull on subscribe.
- `mark_online`/`mark_offline` now publish a `presence_update` event via `realtime_service.publish_presence_event` — but **only on the actual edge** (0→1 connections for online, 1→0 for offline), never on every individual device connect/disconnect, and only onto that one user's own presence channel (`presence_events:{user_id}`, distinct from their `user_events:{user_id}` channel — kept separate on purpose so a presence blip can never be confused with "you were added/removed from a chat"). A publish with no subscribers is a no-op in practice — see below.
- WS actions: `subscribe_presence {user_id}` / `unsubscribe_presence {user_id}` (`routers/websocket.py`). Server-side authorization is `crud_private_chat_pair.get_pair_chat_id(session, requester, target)` — reuses the same `PrivateChatPair` PK lookup `get_or_create_private_chat` already relies on — is non-`None` only if a private chat between the two actually exists; otherwise the request gets `{"type": "error", "code": "forbidden"}`. This is what stops a client from watching an arbitrary user's presence just by knowing their id. Subscribing to yourself is also rejected (`bad_request`). A successful subscribe gets an immediate `presence_status {user_id, status, last_seen_at}` reply (the pull), then `presence_update {user_id, status[, last_seen_at]}` events for as long as the subscription stays open (the push).
- `connection_manager` grew a third parallel tracking structure (same shape as its existing per-chat and per-user-channel state): `_presence_subscribers` (target_user_id → watching connection_ids), `_presence_listener_tasks` (one Redis listener per *watched* target, started only when its subscriber count goes 0→1, stopped at 0 again), and `_presence_watches_by_connection` (for cleanup). `disconnect()` was extended to tear down a connection's presence watches the same way it already tears down chat subscriptions — a socket dying doesn't leave a phantom listener running. This is also why an unsubscribed target genuinely receives zero events afterward, not just filtered-client-side ones (verified manually: reconnecting the watched user after `unsubscribe_presence` produces no event on the watcher's socket).
- **Group chats never show online/offline presence, period** — no server code path computes or sends presence for a group, subscribed or not. Groups only ever show typing indicators (see below, not yet built).
- Manually verified end-to-end against the dev containers (subscribe while target offline → correct `presence_status`; target connects → live `presence_update: online`; target's last WS closes → live `presence_update: offline` + a populated `last_seen_at`; unsubscribe then target reconnects → watcher receives nothing; subscribing to a user with no shared private chat → `forbidden`).

### PoC wiring (`poc/index.html`)
- `privateChatOtherUserId` (chat_id → other participant's user id) is populated alongside the pre-existing `privateChatTitles` in `resolvePrivateChatTitle`, from the same `/chats/{id}/members` call — "free" once you're already fetching it for the phone number.
- Exactly **one** active presence subscription at a time (`presenceSubscribedUserId`, a plain variable, not a ref — nothing in the template reads it directly), matching the backend's "only while this specific 1:1 chat is open" contract. `selectChat` unconditionally unsubscribes first, then (private chat only) resolves the other participant's id if not cached and subscribes — guarded on `activeChatId.value === chatId` still holding after that `await`, in case the user already switched chats/to a group while it was in flight.
- `presenceByUserId` (user_id → `{status}`) is updated from both `presence_status` (the initial pull reply) and `presence_update` (live pushes) in `handleWsMessage` — both use `msg.type`, not `msg.event`, since they're a direct reply/targeted push rather than a chat-wide fanout. The backend still sends `last_seen_at` on both (see above) but the PoC deliberately doesn't store or show it — see UI note below.
- Reconnects need explicit handling: a dropped WebSocket (e.g. `uvicorn --reload`, see above) takes the server-side presence subscription down with it, so `ws.onopen` resets `presenceSubscribedUserId = null` and re-subscribes for the currently-open chat if it's a private one — otherwise `subscribeToPresence`'s "already subscribed, no-op" guard would wrongly skip re-sending the request on the new socket. `logout()` also resets both `presenceSubscribedUserId` and `presenceByUserId`.
- UI: `activeChatPresenceLabel` computed (empty for groups or no active chat) renders under the chat header — **teal "online" when the other participant is online, nothing at all otherwise** (no "offline"/"last seen" text — deliberately dropped per product decision, even though the backend still computes and sends `last_seen_at`; revisit `presenceLabelFor` if that's ever wanted back). Verified visually via a real two-browser-context Playwright run against the dev containers: badge shows "online" live the moment the other user connects, disappears entirely the moment their last connection drops, and a group chat's header never shows any presence line at all (member list only).

## Typing indicator — planned, not yet built
- Separate, fully ephemeral event (`typing {chat_id}`, no DB persistence), fanned out to chat participants like `new_message`, with client-side auto-expiry (~5s) instead of a guaranteed `typing_stopped`. Works for both 1:1 and group chats (unlike presence above, which is 1:1-only).
- Designed to extend to other ephemeral activity kinds (e.g. `recording_audio`) via a `kind` field later, without a new endpoint/service.

## Working conventions
- Prefer fixing real bugs found via testing over asking permission, but flag security-relevant or destructive-looking changes clearly instead of silently reverting them.
- When manually verifying against the dev Postgres container, always leave the schema created (not dropped) when done — other running servers depend on it.
- The test suite runs against that same `test_db` and `drop_all`s after every test, so `pytest` wipes whatever is in the dev database. Dump it first (`docker exec linka-test_db-1 pg_dump -U test_user -d test_db --clean --if-exists > dump.sql`) if it holds anything worth keeping, or re-seed afterwards.
