# ADR 0011 — Snowflake ID generation as a standalone Rust gRPC service (unary-only)

Status: Accepted
Date: 2026-09-05

## Context

Every id in Linka (user / chat / message / media) is drawn from the in-process
Python generator `utils/snowflake.py` — a single `SnowflakeGenerator` guarded by a
`threading.Lock`, minting `(ts - EPOCH) << 22 | machine_id << 12 | sequence`.

Two pressures make this the wrong place for it at target scale:

- **Throughput.** At tens of billions of messages, id minting is on the hot path
  of every send. A GIL-bound, lock-guarded Python counter shared across async
  workers is a contention point, and the machine-id space (10 bits) is wasted
  when only one Uvicorn process exists per host (ADR 0007).
- **Correctness of partition routing.** `messages` is RANGE-partitioned by
  `created_at`, and callers only ever hold an `id`; `id_to_datetime_range()`
  decodes the id's 41-bit timestamp back to a `created_at` window for partition
  pruning (`.claude_docs/database_schema.md`). The id timestamp is therefore a
  *routing key*, and it must track wall-clock closely and advance monotonically.

We want id generation to be a small, fast, independently deployable service that
several Python processes/replicas can share without coordinating a machine-id
each.

## Decision

1. **New service `id_service/` — Rust + `tonic` gRPC, one RPC.**
   `proto/snowflake.proto`: `SnowflakeService.NextId(NextIdRequest) → NextIdResponse { string id }`.
   Bit layout is **identical** to `utils/snowflake.py`: epoch `1704067200000`
   (2024-01-01Z), 41-bit ms timestamp, 10-bit node id, 12-bit sequence
   (4096 ids/ms/node). The Python decoders (`id_to_timestamp_ms`,
   `id_to_datetime`, `id_to_datetime_range`) keep working unchanged against ids
   minted by Rust.

2. **Lock-free generator.** Timestamp and sequence are packed into a single
   `AtomicU64` and advanced with a `compare_exchange_weak` CAS loop — no mutex,
   scales across Tokio worker threads. Clock-backward → yield-and-retry until the
   clock catches up (never hands out a possibly-duplicate id). Sequence
   exhaustion within a ms → busy-spin to the next ms.

3. **`id` crosses the wire as a string**, matching the existing
   "Snowflake-id-as-string" rule everywhere else in Linka (JS/JSON lose precision
   past 2^53). `NextIdRequest` is intentionally empty, left open for future
   fields.

4. **Unary RPC only — NO batch / client-side buffering, ever.**
   A `NextIdBatch(count)` was considered and **rejected**. Postgres derives the
   `created_at` partition-routing key directly from the id's timestamp field. If
   a Python process pre-fetched a batch of ids, their embedded timestamps would
   be stale by the time the rows are written — breaking the strict-ish
   chronological ordering the partition-pruning predicate
   (`id_to_datetime_range`, widened only by `MESSAGE_PARTITION_QUERY_SKEW_HOURS`)
   relies on, and risking rows landing outside the window a range query prunes
   to. One id per RPC keeps `id.timestamp ≈ row.created_at` within the existing
   skew budget. The cost (one extra network round-trip per id) is accepted; the
   service is on the same host / pod network and the RPC is a few microseconds of
   work.

5. **`NODE_ID` from the environment, validated at startup.**
   Read `NODE_ID` (env), parse as `u64`, reject if absent or `> 1023` — the
   process exits non-zero rather than starting with a colliding / silently-zero
   node id. This replaces the hardcoded `1`. Operators assign a distinct
   `NODE_ID` per running replica of the id service; the Python
   `SNOWFLAKE_MACHINE_ID` var becomes irrelevant once Python stops minting ids
   locally (kept for now as the fallback generator still exists).

6. **Health checks.** The standard gRPC Health Checking Protocol
   (`grpc.health.v1.Health`) is served, with `SnowflakeService` reported
   `SERVING`. This is what a container orchestrator / load balancer probes;
   `grpc_health_probe` or `grpcurl` can hit it. No separate HTTP port.

7. **Minimal Dockerfile.** Multi-stage: `rust:*-slim` builder → `debian:*-slim`
   (or `distroless`) runtime carrying only the static-ish `id_service` binary and
   `protoc` at build time. Exposes `50051`. Fits the deploy model of ADR 0007 as
   an additional small container.

8. **Python integration.** `utils/id_client.py` — `async next_id() -> int`,
   gated on `config.ID_SERVICE_ADDR`: empty → in-process `utils.snowflake.next_id`
   (unchanged default); set → one unary `NextId` RPC per id, with a
   local-generator fallback on any RPC error/timeout so minting never
   hard-stops. Lazy shared `grpc.aio` channel. Stubs `utils/snowflake_pb2*.py`
   are checked in, regenerated by `scripts/gen_proto.sh` (no build step). Deps:
   `grpcio` + `grpcio-tools`. `utils/snowflake.py`'s **decode** helpers stay.
   Call sites migrated: `auth_service` (user id), `chat_service` ×2 (chat id),
   `messaging/send` ×2 (message + system-message id) — all `await id_client.next_id()`.
   `receipts/receipt_log` and `storage/client` deliberately keep the sync local
   generator: their paths are sync and the id is not a `created_at` routing key
   (receipt-log rows are placed by `occurred_at`; storage ids are object-key
   nonces).

## Consequences

- Id minting now depends on a reachable id-service; a Python-side timeout /
  retry / circuit-break policy is required, and losing the service stalls all
  sends (mitigation: run ≥2 replicas with distinct `NODE_ID`, plus the retained
  local fallback generator).
- Per-id RPC means id-service QPS == total id-mint QPS. At thousands/s this is
  well within a single Rust `tonic` server; the lock-free CAS path is the point.
- Node-id space is 1024. Each id-service replica burns one; ample.
- No DB schema change, no migration. Wire format and bit layout are unchanged, so
  existing rows and all `id_to_*` decoding keep working.
- New build-time toolchain (Rust, `protoc`) and a new container image in the
  deploy. `deploy/` env example and compose file gain `id_service` +
  `NODE_ID`.
- `proto/snowflake.proto` is now a shared contract between the Rust service and
  the Python client; changes to it must stay backward compatible.
